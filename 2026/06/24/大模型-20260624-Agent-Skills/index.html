什么是 Agent Skills——从 MCP 到 Skill 的自然延伸

学完 MCP 之后，你可能会思考一个问题：有了统一协议让 Agent 连接工具，但 Agent 怎么知道用这些工具完成复杂任务？

MCP 解决的是“用什么工具”，Skill 解决的是“怎么用工具完成任务”。两者是互补关系，不是替代关系。

Skill 的本质：一套结构化的指令和资源，教会 AI 完成特定任务，让 AI 按照标准规则干活。

MCP 与 Skill 的对比

维度 MCP Skill
核心解决 “用什么工具” (What) “怎么用工具完成任务” (How)
本质定位 能力供给层 / 协议层 行为规范层 / 方法论固化层
类比 万能插座（硬件接口） 操作手册（软件规范）
加载方式 全量或按需连接工具 渐进式披露（先描述，再按需加载完整指令）
适用场景 工具发现、标准化调用 复杂工作流、经验沉淀、团队协作

为什么行业突然开始重视 Skill？

核心在于 MCP 在实践中暴露了几个问题，而 Skill 恰好提供了补充方案：

MCP 落地痛点 具体表现
Token 消耗太大 加载过多的 MCP Server 会迅速撑爆上下文。比如 GitHub 官方一个 MCP 就定义了 93 个工具，消耗 5.5 万 Token，成本高且容易导致模型“变笨”
模型决策容易“迷糊” 当上下文被塞满各种工具定义后，模型的注意力会被稀释，可能产生幻觉或错误调用工具
流程不稳定 有了工具和数据，但模型的做事方式每次可能不一样，结果不稳定，难以达到工程化要求

Skill 巧妙地解决了这些问题：它的本质是一个包含指令、脚本和资源的文件夹，通过一套“渐进式披露”机制，让模型先只看“简介”（几十个Token），判断有用后再按需加载完整指令和资源。这样既保证了能力的丰富性，又不会撑爆上下文。

Skill 的核心运行机制：渐进式披露

Agent 通过渐进式披露（progressive disclosure）加载Skill，分为三个阶段：

  • 发现阶段：启动时，Agent 仅加载每个可用技能的名称和描述——刚好足以判断何时可能用得上。

  • 激活阶段：当某个任务与技能的描述匹配时，Agent 会将完整的 SKILL.md 指令读入上下文。

  • 执行阶段：Agent 按照指令执行，按需运行附带的代码或加载引用的文件。

完整的指令只在任务需要时才会加载，因此 Agent 可以同时持有大量技能，而上下文占用却很小。

一个真实案例：如果一开始就把 93 个工具定义全塞进上下文，会消耗 5.5 万 Token。而 Skill 只先加载几十个 Token 的描述，等 AI 判断“有用”后，才按需加载完整指令。这正是 Skill 能在不牺牲能力的前提下，大幅降低 Token 消耗的原因。

Skill 与 Prompt、Projects、Subagents 的区别

概念 定义 适用场景
Prompt 临时性的单次指令 一次性问答、简单任务
Project 工作区级别的上下文集合 管理多个相关文件
Subagent 独立运行的子代理 专业化分工、并行处理
Skill 可复用的能力包（指令+脚本+资源） 固化工作流、团队协作、复杂任务自动化

Skill 的核心竞争力在于“可复用”和“结构化”。 你可以把测试专家的工作经验、流程规范、模板全部固化到一个 Skill 文件夹中，团队成员和 AI 都可以按同一套标准执行。
