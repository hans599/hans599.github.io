带规划能力的Agent

Posted on 2026-06-18 Edited on 2026-06-20

前言：为什么需要规划和多工具协同？

  • 单工具Agent的局限性（只能一问一答，无法处理复杂任务）

  • 复杂任务的典型特征：多步骤、有依赖关系、需要动态决策

工具调用模式的演进

  • 模式一：循环式工具选择（Function Calling）—— 模型逐轮决策，适合简单任务

  • 模式二：计划驱动执行（Plan-then-Execute）—— 先生成全局计划，再执行，适合多步任务

  • 模式三：程序化工具编排—— 将复杂逻辑下沉到代码，适合大规模数据处理

参考博客：大模型工具使用的三次进化：从 Function Calling 到程序化编排

Plan-and-Solve：让Agent学会先规划

Plan-and-Solve的核心思想：先制定计划，再按计划执行。减少盲目调用，提高任务完成率

  • OpenAI和Anthropic的实践：引导模型在调用工具前进行显式规划

  • 规划工具的实现方式：通过一个“思考与规划”工具让模型结构化输出

为什么规划能提升效果？

  • 减少盲目调用：有全局视角，避免“走一步看一步”的试错
  • 提高任务完成率：明确依赖关系（例如先分析结构，再统计指标，最后生成文档）

扩展： LangGraph使用工具调用错误处理

LangGraph 将Agent 建模为一组离散的步骤（节点），这些步骤以图的形式组织。对于一个典型的 Agent，这包括：一个调用模型的节点，一个执行模型返回的工具调用的节点，以及你希望围绕这个循环添加的任何确定性逻辑。由于 LangGraph 控制执行流程，因此它也是你处理这些步骤中任何一个失败时该做什么的地方。

LangGraph提供了三层容错机制，让Agent在生产环境中更健壮 fault-tolerance-in-langgraph

  • RetryPolicy（重试策略）：针对临时性错误，使用退避/抖动机制自动重试。

  • TimeoutPolicy（超时策略）：对单次节点尝试设置基于挂钟时间或进度上限。

  • error_handler（错误处理节点）：在重试次数用尽后运行的节点，并附带失败上下文。

上述三种容错原语可以轻松组合使用，但它们真正的用武之地，是那些会产生副作用（即实际修改外部状态）的工作流。典型的例子就是航班预订：这不是一步就能完成的操作，而是一连串必须按顺序执行的动作——先预留座位，再扣费，最后出票。每一步都要调用外部系统，任何一步都可能出问题。

如果图省事，直接整段重试，很快就会碰上麻烦。举个例子：座位已经预留好了，但扣费或者出票失败了，这时候预留的座位就挂在系统里，不上不下，成了脏数据。

真正合理的做法是：每一小步单独重试；如果某一步反复重试还是失败，就撤销之前所有已经成功执行的步骤（包括失败的那一步本身，因为你无法确定它到底留下了什么状态）。

这其实就是经典的 SAGA 模式（要么全成功，要么通过补偿操作全部回滚）。在分布式系统里，当无法把所有操作装进一个数据库事务时，这是处理失败场景的标准解法。SAGA 模式把一个大事务拆成一组本地事务（步骤），并为每个步骤定义对应的补偿操作（Compensation）:
