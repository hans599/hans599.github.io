# 前言：为什么需要规划和多工具协同？  
  
- 单工具Agent的局限性（只能一问一答，无法处理复杂任务）

- 复杂任务的典型特征：多步骤、有依赖关系、需要动态决策


<!-- more --> 


# 工具调用模式的演进

- 模式一：循环式工具选择（Function Calling）—— 模型逐轮决策，适合简单任务

- 模式二：计划驱动执行（Plan-then-Execute）—— 先生成全局计划，再执行，适合多步任务

- 模式三：程序化工具编排—— 将复杂逻辑下沉到代码，适合大规模数据处理

参考博客：[大模型工具使用的三次进化：从 Function Calling 到程序化编排](https://www.datalearner.com/blog/llm-tool-use-evolution-programmatic-calling)



# Plan-and-Solve：让Agent学会先规划

Plan-and-Solve的核心思想：先制定计划，再按计划执行。减少盲目调用，提高任务完成率


- OpenAI和Anthropic的实践：引导模型在调用工具前进行显式规划

- 规划工具的实现方式：通过一个“思考与规划”工具让模型结构化输出


参考博客：
[如何让 Agent 规划调用工具](https://news.qq.com/rain/a/20250522A01SKV00?suid=&media_id=)


为什么规划能提升效果？
- 减少盲目调用：有全局视角，避免“走一步看一步”的试错
- 提高任务完成率：明确依赖关系（例如先分析结构，再统计指标，最后生成文档）

论文支持：ReAct论文和后续研究都表明，显式规划能显著提升多步任务的成功率 
[Architecting Resilient LLM Agents:
A Guide to Secure Plan-then-Execute Implementations](https://browse-export.arxiv.org/pdf/2509.08646#6#4)


简单代码示例：
```py
def planner_node(state: AgentState):
    """规划节点：LLM生成执行计划"""
    prompt = f"""
    用户需要分析以下Python代码并生成文档。
    
    可用工具：
    1. analyze_code_structure - 解析代码结构
    2. count_code_metrics - 统计代码指标
    3. generate_doc_template - 生成文档模板
    
    请制定一个执行计划，按顺序列出需要调用的工具。
    计划格式：
    Step 1: [工具名] - [目的]
    Step 2: [工具名] - [目的]
    ...
    """
    response = llm.invoke(prompt)
    return {"plan": response.content}
```


# Self-Refine：让Agent学会自我反思

Self-Refine：让Agent评估自己的输出，发现问题后自动修正，模拟人类的“写完检查一遍”过程

核心流程：
```
生成 → 评估 → 合格？→ 是 → 输出
              ↓ 否
            修正 → 重新评估
```

在LangGraph中通过条件边实现，
```py
def reviewer_node(state: AgentState):
    """审查节点：检查文档质量，决定是否重新生成"""
    prompt = f"""
    请审查以下文档，判断质量：
    {state["doc"]}
    
    评估标准：
    1. 是否包含所有函数/类的说明？
    2. 参数描述是否完整？
    3. 是否有示例代码？
    
    如果质量合格，回复 PASS。
    如果需改进，明确指出问题，回复 IMPROVE: [问题描述]
    """
    response = llm.invoke(prompt)
    return {"review": response.content}

def should_continue(state):
    """条件边：决定下一步是结束、重试还是转人工"""
    # 1. 如果审查通过
    if "PASS" in state["review"]:
        return END
    # 2. 如果超过最大重试次数，转人工审查
    if state["iteration"] >= 3:
        return "human_reviewer"  # 名称改为 human_reviewer
    
    # 3. 否则，重新生成
    return "doc_generator"

# 然后，在 workflow 中添加一个 'human_reviewer' 节点
workflow.add_node("human_reviewer", human_review_node)
    
```

研究表明，在Plan-then-Execute架构中加入重规划节点（replanner），能让Agent根据执行结果动态调整计划，显著提升鲁棒性。
[Architecting Resilient LLM Agents:
A Guide to Secure Plan-then-Execute Implementations](https://browse-export.arxiv.org/pdf/2509.08646#6#4)

重规划节点接收：1. 原始目标；2. 当前计划；3. 已执行步骤及其结果。然后判断：继续执行、生成新计划，还是任务完成。

# 扩展： LangGraph使用工具调用错误处理

LangGraph 将Agent 建模为一组离散的步骤（节点），这些步骤以图的形式组织。对于一个典型的 Agent，这包括：一个调用模型的节点，一个执行模型返回的工具调用的节点，以及你希望围绕这个循环添加的任何确定性逻辑。由于 LangGraph 控制执行流程，因此它也是你处理这些步骤中任何一个失败时该做什么的地方。

LangGraph提供了三层容错机制，让Agent在生产环境中更健壮 [fault-tolerance-in-langgraph](https://www.langchain.com/blog/fault-tolerance-in-langgraph)


- RetryPolicy（重试策略）：针对临时性错误，使用退避/抖动机制自动重试。

- TimeoutPolicy（超时策略）：对单次节点尝试设置基于挂钟时间或进度上限。

- error_handler（错误处理节点）：在重试次数用尽后运行的节点，并附带失败上下文。




上述三种容错原语可以轻松组合使用，但它们真正的用武之地，是那些会产生副作用（即实际修改外部状态）的工作流。典型的例子就是航班预订：这不是一步就能完成的操作，而是一连串必须按顺序执行的动作——先预留座位，再扣费，最后出票。每一步都要调用外部系统，任何一步都可能出问题。

如果图省事，直接整段重试，很快就会碰上麻烦。举个例子：座位已经预留好了，但扣费或者出票失败了，这时候预留的座位就挂在系统里，不上不下，成了脏数据。

真正合理的做法是：每一小步单独重试；如果某一步反复重试还是失败，就撤销之前所有已经成功执行的步骤（包括失败的那一步本身，因为你无法确定它到底留下了什么状态）。

这其实就是经典的 SAGA 模式（要么全成功，要么通过补偿操作全部回滚）。在分布式系统里，当无法把所有操作装进一个数据库事务时，这是处理失败场景的标准解法。SAGA 模式把一个大事务拆成一组本地事务（步骤），并为每个步骤定义对应的补偿操作（Compensation）:

```
正常流程（T1, T2, T3 ...）：
┌─────────┐   ┌─────────┐   ┌─────────┐
│ T1:     │ → │ T2:     │ → │ T3:     │ → 成功
│ 预留座位 │   │ 扣费    │   │ 出票    │
└─────────┘   └─────────┘   └─────────┘

失败流程（T2 失败，触发补偿）：
┌─────────┐   ┌─────────┐   ┌─────────┐
│ T1:     │ → │ T2:     │ → │ C1:     │ → 回滚完成
│ 预留座位 │   │ 扣费 ❌  │   │ 释放座位 │
└─────────┘   └─────────┘   └─────────┘
```


下面就是用 LangGraph 实现 SAGA 模式的代码示例：

```py
from typing import TypedDict, Annotated, Literal
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, RetryPolicy
from langgraph.errors import NodeError

# ========== 重试策略配置 ==========
# 适用于：网络请求、API调用、数据库操作等可能因临时故障失败的场景
policy = RetryPolicy(
    # 首次重试前的等待时间（秒）
    # 第1次失败后，等待 0.5 秒再重试
    initial_interval=0.5,
    
    # 退避因子（指数退避的倍数）
    # 每次重试间隔按此倍数增长：0.5s → 1.0s → 2.0s → 4.0s ...
    backoff_factor=2.0,
    
    # 最大等待间隔（秒）
    # 防止无限增长，最多等待 128 秒
    # 实际间隔 = min(计算出的间隔, max_interval)
    max_interval=128.0,
    
    # 最大尝试次数（包含首次执行）
    # 首次执行 + 最多2次重试 = 总共3次机会
    max_attempts=3,
    
    # 是否启用随机抖动（建议开启）
    # 在计算出的等待时间上增加随机偏移（0~1秒）
    # 作用：防止多个服务同时重试，造成"雪崩效应"
    jitter=True,
    
    # 触发重试的异常类型（白名单）
    # 只有这些异常才触发重试，其他异常直接失败
    # 也可以传入 callable 函数自定义判断逻辑
    retry_on=(ConnectionError, TimeoutError),  # 网络连接超时才重试
    # 可选写法：
    # retry_on=lambda e: isinstance(e, (ConnectionError, TimeoutError))
)


# 定义状态结构
class BookingState(TypedDict, total=False):
    booking_id: str          # 预订ID
    passenger: str           # 乘客姓名
    flight: str              # 航班信息
    seat: str                # 座位号（座位预订成功后分配）
    amount: int              # 需扣费金额（以最小货币单位计）
    payment_ref: str         # 支付参考号（支付成功后设置）
    ticket_no: str           # 票号（出票成功后设置）
    completed: Annotated[list[str], operator.add]  # 累加已完成的步骤列表


def to_compensate(state: BookingState, error: NodeError) -> Command:
    """将重试用尽的步骤路由到补偿节点"""
    return Command(
        # 记录失败的节点
        update={"completed": [f"FAILED:{error.node}"]},
        goto="compensate",
    )


def reserve_seat(state) -> BookingState:
    """调用座位库存服务，为此行程预留座位"""
    ...
    return {"seat": "12A", "completed": ["reserve_seat"]}


def process_payment(state) -> BookingState:
    """在座位预留期间，通过支付处理器扣费"""
    ...
    return {"payment_ref": "pay_abc123", "completed": ["process_payment"]}


def issue_ticket(state) -> BookingState:
    """确认座位，支付成功后出票"""
    ...
    return {"ticket_no": "TKT-7788", "completed": ["issue_ticket"]}


def compensate(state) -> Command[Literal["__end__"]]:
    """检查已完成步骤，按逆序撤销实际执行过的步骤，确保预订操作要么全部成功，要么全部回滚"""
    if "issue_ticket" in state["completed"]:
        void_ticket(state)      # # 补偿 T3：作废票 
    if "process_payment" in state["completed"]:
        refund_payment(state)   # # 补偿 T2：退款
    if "reserve_seat" in state["completed"]:
        release_seat(state)     # # 补偿 T1：释放座位
    return Command(goto=END)


# 构建图
graph = (
    StateGraph(BookingState)
    # 所有步骤共享相同的重试策略和回退目标（每步骤仍可单独覆盖）
    .set_node_defaults(retry_policy=RETRYABLE, error_handler=to_compensate)
    .add_node("reserve_seat", reserve_seat)      # 步骤1：预留座位
    .add_node("process_payment", process_payment) # 步骤2：处理支付
    .add_node("issue_ticket", issue_ticket)      # 步骤3：出票
    .add_node("compensate", compensate)          # 补偿节点
    .add_edge(START, "reserve_seat")             # 起点 → 预留座位
    .add_edge("reserve_seat", "process_payment") # 预留座位 → 处理支付
    .add_edge("process_payment", "issue_ticket") # 处理支付 → 出票
    .add_edge("issue_ticket", END)               # 出票 → 终点
    .compile(checkpointer=checkpointer)
)
```
