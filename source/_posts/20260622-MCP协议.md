# 为什么需要MCP？


在AI Agent开发中，一个反复出现的痛点是如何让大模型调用外部工具。传统方式下，每个工具都要单独写适配代码——模型A用一种Function Call格式，模型B用另一种，工具用Python写一套接口，用C++写又要重新封装。这种“碎片化”集成方式难以扩展。

MCP（Model Context Protocol）正是为解决这一问题而生。它由Anthropic于2024年底提出并开源，被视作AI领域的“USB-C接口”——为AI助手连接任何数据源或服务提供了统一标准。

MCP的核心理念：在LLM与外部世界之间建立标准化、双向的通信通道。过去M个模型对接N个工具需要M×N种适配，现在有了通用协议，不同模型与不同工具可以通过MCP这一“共同语言”无缝协作。

推荐阅读：[MCP Python SDK](https://pypi.org/project/mcp/1.19.0/)

# MCP核心概念速览

MCP遵循经典的客户端-服务器模型，包含三个主要组件 ：
| 组件 | 角色 | 说明 |
| :--- | :--- | :--- |
| Host（主机） | 运行 AI 模型的应用 | AI 助手应用、IDE 插件等 |
| Client（客户端） | Host 内部的 MCP 客户端 | 负责与外部 MCP 服务器通信 |
| Server（服务器） | 独立运行的服务 | 按照 MCP 协议对外提供能力 |


每个MCP Server对外暴露能力时，主要包含三种元素：
- Resources（资源）：服务器开放的数据内容，如文件、数据库记录。类似REST中的GET端点。
- Tools（工具）：可执行的操作，模型可以调用的函数。带有明确的参数结构（JSON Schema定义）。
- Prompts（提示模板）：可复用的提示词模板或交互流程。

MCP的设计注重动态发现：客户端连接服务器时，会先请求其能力描述，服务器返回支持的Tools列表、资源类型、参数要求等信息。这意味着服务端可以随时升级功能而不破坏兼容性。

MCP vs Function Calling

| 维度       | Function Calling                                   | MCP                              |
| :--------- | :------------------------------------------------- | :------------------------------- |
| 标准化程度 | 各家模型格式不统一（OpenAI、Anthropic 各有各的格式） | 统一协议，跨模型通用              |
| 动态发现   | 需要硬编码工具定义                                  | 服务端自描述，动态获取            |
| 语言支持   | 通常绑定特定 SDK                                    | 多语言（Python/TS/C++/Java...）   |
| 通信方式   | 一般是 HTTP/REST                                    | 支持 Stdio、SSE、Streamable HTTP |
| 适用场景   | 简单单工具调用                                      | 复杂多工具、跨语言、大规模集成     |

MCP的价值在于解耦：工具开发者只需要实现一个MCP Server，任何支持MCP的Client都可以调用它，无需为每个模型单独适配。


# 通信机制：Stdio与SSE

MCP支持多种传输方式，最常用的是两种：Stdio与SSE

| 对比项       | Stdio                         | SSE                                              |
| :----------- | :---------------------------- | :----------------------------------------------- |
| 通信方式     | 标准输入/输出（stdin/stdout） | HTTP + Server-Sent Events                        |
| 启动方式     | 客户端 `subprocess` 启动      | 独立启动（例如`npm run dev`或`python server.py`） |
| 进程管理     | 客户端创建子进程，管理生命周期 | 服务器独立运行，客户端连接                         |
| 网络要求     | 无需网络，本地进程通信         | 需要网络（HTTP）                                  |
| 适用场景     | 本地工具、命令行工具           | 远程服务、多客户端共享                             |
| 跨语言支持   | 需要语言能创建子进程           | 任何语言都能通过 HTTP 通信                         |
| 调试         | 日志必须输出到 `stderr`       | 日志可以输出到 `stdout`/文件                      |
| 进程生命周期 | 随客户端结束而结束             | 独立运行，持续服务                                |

## Stdio 模式 = "客户端启动脚本"

```text
你的 Python 代码 (Client)
         │
         │ 1. 创建子进程
         ▼
    python server_python_stdio.py
         │
         │ 2. 通过 stdin/stdout 通信（JSON-RPC）
         ▼
    客户端 ←→ 子进程（MCP Server）
         │
         │ 3. 子进程退出时，通信结束
         ▼
    客户端继续执行
```

关键点：

- Server 不需要预先启动，客户端自己创建子进程
- 通信管道：stdin（客户端→服务器）和 stdout（服务器→客户端）
- stderr 用于日志，不影响协议通信


为什么 Stdio 模式要求日志输出到 stderr？

```txt
MCP Stdio 通信原理
┌─────────────────────────────────────────────────────┐
│  客户端（Parent Process）                           │
│                                                     │
│   stdin  ───────────────┐                          │
│                         │                          │
│   stdout ◄──────────────┼─────────────────┐        │
│                         │                 │        │
│   stderr  ──────────────┘                 │        │
│          （日志/调试信息）                  │        │
│                                            │        │
└────────────────────────────────────────────┘        │
                                                     │
                    ┌────────────────────────────────┘
                    ▼
         ┌──────────────────────────────────────────┐
         │  子进程（MCP Server）                     │
         │                                          │
         │  stdout → 只输出 JSON-RPC 消息           │
         │  stderr → 输出日志、错误信息              │
         └──────────────────────────────────────────┘
```
- stdout：只能传输 JSON-RPC 消息，任何额外的文本都会导致客户端解析失败
- stderr：可以自由输出日志，不会影响协议通信






## SSE 模式 = "先启动 Server，再连接"

```txt
# 终端1：预先启动 Server
python server_sse.py
🚀 Server running on http://0.0.0.0:8080/sse

# 终端2：客户端连接
Client ──HTTP GET /sse──► Server
       ◄──SSE 事件流────
       ──HTTP POST /messages──►
       ◄──响应─────────
```
关键点：
- Server 必须预先启动（独立运行）
- 通过网络（HTTP）通信
- 支持多个客户端同时连接


## JSON-RPC
JSON-RPC 是一个轻量级的远程过程调用协议，用 JSON 格式来传输数据。
核心思想： 我想调用你机器上的一个函数，但我们不在同一个进程里。
请求格式
```json
{
  "jsonrpc": "2.0",
  "method": "circle_area",
  "params": { "radius": 5 },
  "id": 1
}
```
- method — 要调用的函数名
- params — 参数
- id — 请求编号，用来匹配响应

响应格式
```json
{
  "jsonrpc": "2.0",
  "result": { "area": 78.54 },
  "id": 1
}

```
MCP 协议底层就是 JSON-RPC 2.0，Python 客户端调用 session.call_tool("circle_area", {...}) 时，SDK 自动把它打包成 JSON-RPC 请求发出去，TypeScript 服务器收到后解包执行，再把结果打包成 JSON-RPC 响应返回。

## 主要踩坑点


**坑1：SSE 服务器返回 400**
Python 客户端连接 TypeScript SSE 服务器时，/messages 端点一直返回 400。
服务器日志显示 Body 解析完全正常，请求体也收到了，但 handlePostMessage 内部报错。
根本原因： 新版 SDK（1.x）的 handlePostMessage 签名变了，需要显式传入第三个参数 req.body，否则内部解析不到请求体。


```ts
// ❌ 旧写法
await transport.handlePostMessage(req, res);

// ✅ 新写法
await transport.handlePostMessage(req, res, req.body);
```

如何定位： 直接看官方示例源码：
```bash
cat node_modules/@modelcontextprotocol/sdk/dist/cjs/examples/server/simpleSseServer.js
```

**坑2：SSE 连接地址写成了 0.0.0.0**
```py
# ❌ 0.0.0.0 是服务器监听地址，客户端不能连这个
"url": "http://0.0.0.0:8080/sse"

# ✅ 客户端连接用 127.0.0.1
"url": "http://127.0.0.1:8080/sse"
```


**坑3：Pydantic 字段名不能以下划线开头**
动态构建 Pydantic 模型时，为没有参数的工具添加了占位字段 _placeholder，Pydantic 直接抛出：
```txt
NameError: Fields must not use names with leading underscores;
e.g., use 'placeholder' instead of '_placeholder'.
```

这个错误被 TaskGroup 包了两层，日志看起来像连接失败，实际是 Schema 构建失败。
修复：
```py
# ❌
fields["_placeholder"] = (str, Field(default="", description="占位"))
kwargs.pop("_placeholder", None)

# ✅
fields["placeholder"] = (str, Field(default="", description="占位"))
kwargs.pop("placeholder", None)
```


**坑4：模型太小导致工具调用死循环**

使用 qwen2.5:3b 时，工具调用成功后模型仍然反复调用同一个工具，无法停止。
原因是 3b 模型指令跟随能力不足，无法理解"调用一次后停止"的要求，系统提示也基本无效。

解法一：换更大的模型（根本解法）
```py
model="qwen3.5:4b"  # qwen3.5 系列指令跟随明显更好
```

同时优化promt
```py
        initial_state = {
            "messages": [
                SystemMessage(content="""你是一个工具调用助手，使用中文回复。
                规则：
                1. 根据用户问题选择合适的工具调用一次
                2. 工具返回结果后，直接用简洁的中文总结结果回复用户
                3. 不要询问用户是否需要更多帮助，不要重复调用工具
                """),
                HumanMessage(content=query)
            ]
        }
```

解法二：加递归限制兜底
