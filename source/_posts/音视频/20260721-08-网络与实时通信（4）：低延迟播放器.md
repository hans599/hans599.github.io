监控画面、视频连线、云游戏——这些场景对延迟极其敏感。画面里发生的事情和你在屏幕上看到的差距如果超过 500ms，交互体验就会明显变差。这篇文章系统地拆解延迟的来源，然后逐一砍掉。

# 延迟从哪里来

把时间线拉长，端到端延迟是这些环节的累加：

```mermaid
flowchart LR
    A[采集] -->|30~60ms| B[编码]
    B -->|10~50ms| C[打包/网络]
    C -->|10~100ms| D[Jitter Buffer]
    D -->|50~500ms| E[解码]
    E -->|5~20ms| F[渲染缓冲]
    F -->|16~50ms| G[屏幕显示]
```

每一段都会贡献延迟，总延迟 = 所有段之和。常规播放器（如 VLC 默认配置）端到端延迟轻松超过 1 秒。砍到 500ms 以内，需要在这几段上同时发力。

| 延迟环节 | 常规配置 | 低延迟配置 | 优化手段 |
|----------|----------|------------|----------|
| 编码 | 50~100ms | 5~20ms | ultrafast preset, 无 B 帧 |
| 网络 | 10~50ms | 5~10ms | UDP 传输，调整 MTU |
| Jitter Buffer | 500~2000ms | 30~100ms | 动态调节，最小化缓冲 |
| 解码缓冲 | 100~500ms | 1~3 帧 | 缩减 frame queue |
| 渲染 | 2~3 帧 vsync | 1 帧 | 关闭多重缓冲 |

# 编码端：速度优先于压缩率

编码是延迟的第一大项。x264 默认的 `medium` preset 编码一帧 1080p 需要 20~50ms，加上 B 帧的延迟（等后面的帧到了才能编码），编码延迟轻松 100ms+。

**低延迟编码配置**：

```c
AVCodecContext *low_latency_encoder(int width, int height, int fps) {
    AVCodecContext *enc = avcodec_alloc_context3(
        avcodec_find_encoder(AV_CODEC_ID_H264));
    
    enc->width    = width;
    enc->height   = height;
    enc->time_base = (AVRational){1, fps};
    enc->framerate = (AVRational){fps, 1};
    enc->pix_fmt  = AV_PIX_FMT_YUV420P;
    enc->bit_rate = 2000000;
    
    // ──── 低延迟核心配置 ────
    enc->max_b_frames = 0;          // 关 B 帧，零重排序延迟
    enc->gop_size     = fps * 1;    // GOP 1 秒（可接受的关键帧间隔）
    enc->delay        = 0;          // 显式设 0 延迟
    
    av_opt_set(enc->priv_data, "preset",    "ultrafast", 0);
    av_opt_set(enc->priv_data, "tune",      "zerolatency", 0);
    av_opt_set(enc->priv_data, "profile",   "baseline", 0);
    av_opt_set(enc->priv_data, "rc-lookahead", "0", 0);  // 码控不看未来帧
    av_opt_set(enc->priv_data, "sync-lookahead", "0", 0);
    av_opt_set(enc->priv_data, "sliced-threads", "1", 0); // 切片级多线程
    
    avcodec_open2(enc, avcodec_find_encoder(AV_CODEC_ID_H264), NULL);
    return enc;
}
```

**硬件编码**还可以再省一截：NVIDIA NVENC、Intel QSV、AMD AMF 的编码延迟通常在 5~10ms，比软件 `ultrafast` 还快一倍。FFmpeg 中配置 NVENC：

```c
const AVCodec *codec = avcodec_find_encoder_by_name("h264_nvenc");
av_opt_set(enc->priv_data, "preset",  "p1", 0);     // NVENC 最低延迟
av_opt_set(enc->priv_data, "tune",    "ll", 0);      // low latency
av_opt_set(enc->priv_data, "delay",   "0", 0);
av_opt_set(enc->priv_data, "zerolatency", "1", 0);
```

# 解码缓冲：最多 1~2 帧

常规播放器的解码缓冲通常有 5~15 帧——这是为了应对解码耗时波动和音视频同步。但在低延迟场景下，这个缓冲必须砍掉。

```c
// 常规配置：frame queue = 10~15 帧，延迟 300~500ms
#define FRAME_QUEUE_SIZE 15

// 低延迟配置：frame queue = 2 帧，延迟 30~60ms
#define FRAME_QUEUE_SIZE  2   // 1 帧解码中 + 1 帧待渲染
```

帧队列缩小之后，解码线程的阻塞几率会增大——队列满了就得等。解决方法是让解码线程不阻塞等待渲染，而是**直接覆盖队列中最老的帧**：

```c
typedef struct {
    AVFrame *frames[FRAME_QUEUE_SIZE];
    int write_idx;
    int read_idx;
    int count;
    SDL_mutex *mutex;
    SDL_cond *cond;
} LowLatencyFrameQueue;

// 非阻塞写入——如果队列满了，覆盖最老的帧
int ll_queue_push_force(LowLatencyFrameQueue *q, AVFrame *frame) {
    SDL_LockMutex(q->mutex);
    
    if (q->count >= FRAME_QUEUE_SIZE) {
        // 队列满：丢弃最老的那帧，释放空间
        av_frame_unref(q->frames[q->read_idx]);
        q->read_idx = (q->read_idx + 1) % FRAME_QUEUE_SIZE;
        q->count--;
    }
    
    av_frame_ref(q->frames[q->write_idx], frame);
    q->write_idx = (q->write_idx + 1) % FRAME_QUEUE_SIZE;
    q->count++;
    
    SDL_CondSignal(q->cond);
    SDL_UnlockMutex(q->mutex);
    return 0;
}
```

丢帧不可避免——牺牲完整帧率换取低延迟。对于监控和互动场景，观众对偶尔丢一帧的感知远低于 500ms 的延迟。

# Jitter Buffer：按场景调节

Jitter Buffer 是延迟的大户。常规播放器的缓冲通常在 500ms~2 秒，砍到 30~80ms 是低延迟的关键。

```c
void configure_jitter_buffer_for_low_latency(JitterBuffer *jb, 
                                              int scenario) {
    switch (scenario) {
    case SCENARIO_LAN:           // 局域网，极低抖动
        jb->min_delay_ms = 10;
        jb->max_delay_ms = 50;
        jb->target_delay_ms = 20;
        break;
        
    case SCENARIO_WAN:           // 公网，中等抖动
        jb->min_delay_ms = 30;
        jb->max_delay_ms = 150;
        jb->target_delay_ms = 60;
        break;
        
    case SCENARIO_4G:            // 移动网络，高抖动
        jb->min_delay_ms = 50;
        jb->max_delay_ms = 300;
        jb->target_delay_ms = 100;
        break;
    }
}
```

配合 **NACK（Negative Acknowledgement）** 机制：如果接收端发现某个 RTP 包丢了，立即向发送端请求重传，而不是等 Jitter Buffer 超时后才丢弃。重传一两个包只需要多等 10~20ms，远优于丢一整帧。

```c
// NACK：检测到丢包时立即请求重传
void on_packet_loss(uint16_t missing_seq, struct sockaddr_in *sender) {
    // 构造 RTCP NACK 包（通过 RTCP Feedback 消息）
    uint8_t nack_packet[28];
    build_rtcp_nack(nack_packet, missing_seq);
    sendto(rtcp_sock, nack_packet, sizeof(nack_packet), 0,
           (struct sockaddr *)sender, sizeof(*sender));
}
```

NACK 是 WebRTC 中降低延迟的核心手段之一——与其等 Jitter Buffer 超时（100ms+），不如主动要包（单次 RTT）。

# 渲染管线：绕过 vsync 的双缓冲

多数播放器用 OpenGL 的默认双缓冲（double buffering），这意味着渲染线程画完一帧后要等下一次 vsync 才能交换到屏幕。60Hz 显示器的 vsync 间隔是 16.6ms，双缓冲会引入额外的 16~33ms 延迟。

```c

// 更适合低延迟的是：单缓冲 + 自控交换时机

// 方案二：OpenGL 自适应 vsync
// NVIDIA: glfwSwapInterval(0) 完全关 vsync（可能撕裂但延迟最低）
// 更好的: 在延迟和撕裂之间折中

// 方案三：Windows 的 DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT
// 允许精确控制最多排队几帧
// 这是 Windows 下低延迟渲染的标准做法
```

对于跨平台的简单方案，用 `glFlush` + `glFinish` 精确控制 GPU 管线：

```c
void render_low_latency(VideoWidget *w, uint8_t *rgb_data) {
    glTexImage2D(GL_TEXTURE_2D, 0, GL_RGB, 
                 w->frame_w, w->frame_h, 0,
                 GL_RGB, GL_UNSIGNED_BYTE, rgb_data);
    
    glDrawElements(GL_TRIANGLES, 6, GL_UNSIGNED_INT, 0);
    glFinish();  // 强制等待 GPU 完成当前帧，减少排队
    
    w->swapBuffers();
}
```

# 音频延迟：小缓冲 = 低延迟

SDL2 默认音频缓冲是 4096 个采样点，在 48kHz 下相当于 85ms。降到 512 采样点就只剩 10ms：

```c
SDL_AudioSpec want;
want.freq    = 48000;
want.format  = AUDIO_S16SYS;
want.channels = 2;
want.samples = 512;  // 512 采样点 = 10.7ms @48kHz（低延迟）
                     // 默认 4096 = 85.3ms（常规延迟）
want.callback = audio_callback;

SDL_AudioDeviceID dev = SDL_OpenAudioDevice(NULL, 0, &want, &have, 0);
```

但缓冲太小也有副作用——音频回调被调用的频率太高（1024 采样点 = 每秒回调 46 次），CPU 开销变高。而且如果解码线程偶尔供不上数据，爆音的概率也更大。512 是一个不错的平衡点，低于 256 则风险大于收益。

# 将延迟"可视化"：Glass-to-Glass 测量

口说无凭，需要一把"尺子"来量端到端延迟。最简单的方法——**秒表法**：

1. 手机上开一个毫秒计时器
2. 用摄像头对着手机屏幕
3. 在接收端屏幕上看这个画面
4. 拍照，用手机上的时间和屏幕上的时间差值 = 端到端延迟

代码层面可以做更精确的测量——在采集端用 `av_gettime_relative()` 记录每帧的时间戳，嵌入 SEI（H.264 的 Supplemental Enhancement Information），接收端解码 SEI，当前时间减原始时间戳：

```c
// 发送端：把采集时间戳写入 H.264 SEI
void inject_timing_sei(AVCodecContext *enc, AVFrame *frame) {
    int64_t now = av_gettime_relative();
    // 构造 SEI NAL 单元，写入 now...
    // 在 encode 之前插入到 frame 的 side data 中
}

// 接收端：解码后读取 SEI
int64_t capture_time = extract_timing_sei(decoded_frame);
int64_t now = av_gettime_relative();
int64_t e2e_latency_us = now - capture_time;

printf("端到端延迟: %.1f ms\n", e2e_latency_us / 1000.0);
```

有了这个测量，你才能真正知道哪一段优化有效、哪一段在做无用功。不要猜，要量。

# 延迟预算表

以 500ms 为目标，给每个环节分配预算：

| 环节 | 预算 | 实现手段 |
|------|------|----------|
| 采集 | 30ms | 摄像头自身延迟，硬件决定 |
| 编码 | 15ms | ultrafast preset 或无 B 帧硬编码 |
| 网络传输 | 20ms | 局域网 UDP，公网另算 |
| Jitter Buffer | 40ms | 局域网 30~50ms 缓冲 |
| 解码 | 10ms | 硬解或 ultrafast 的软解 |
| 帧队列 | 33ms | queue size=2 @30fps |
| 渲染 vsync | 16ms | 单缓冲 @60Hz |
| **总计** | **~164ms** | **远低于 500ms 目标** |

局域网场景下做到 200ms 以内是完全可行的。公网场景（加上 50~150ms 的网络 RTT + 公网 Jitter Buffer 100ms），做到 300~500ms 也是可预期的。

# 小结

低延迟不是单一技术点，是对**整条管线的系统优化**：

| 优化点 | 从 | 到 | 省多少 |
|--------|----|----|--------|
| 编码 preset | medium | ultrafast | 30~80ms |
| B 帧 | 2 帧 | 0 帧 | 66ms @30fps |
| Jitter Buffer | 1000ms | 40ms | 960ms |
| 帧队列 | 15 帧 | 2 帧 | 430ms @30fps |
| 音频缓冲 | 4096 samples | 512 samples | 75ms |

砍掉这些，就能从默认的 1~2 秒降到 100~200ms（局域网）或 300~500ms（公网）。这 12 篇文章串起来，音视频开发的完整技能树——从理论到解码、从播放到推流、从网络协议到延迟优化——就都有了底层的代码理解和直接的实践路径。
