# 前言：为什么需要RAG？

- RAG，检索增强生成（Retrieval-Augmented Generation），RAG 是一种将外部知识库检索与 LLM 生成相结合的技术架构，旨在解决大模型的知识截止、幻觉、无法访问私有数据等核心问题。


<!-- more --> 

- RAG vs 微调，者不是"二选一"的关系，而是互补的技术，各有优劣。


```py
用户需求
    │
    ▼
┌─────────────────────────────────────┐
│ 是否需要访问实时/私有/外部知识？     │
└─────────────────────────────────────┘
    │                    │
   是                   否
    │                    │
    ▼                    ▼
┌──────────────┐   ┌──────────────────┐
│   用 RAG     │   │ 是否需要改变     │
│             │   │ 模型的风格/能力？  │
└──────────────┘   └──────────────────┘
                         │          │
                        是         否
                         │          │
                         ▼          ▼
                  ┌──────────┐  ┌──────────┐
                  │  微调    │  │ 普通 LLM │
                  └──────────┘  └──────────┘

常见组合：
- 知识问答 → RAG
- 风格化客服 → 微调 + RAG
- 代码生成 → 微调
- 内部助手 → 微调（高频问题）+ RAG（实时政策）

```

- 本博客目标：上传PDF → 检索相关内容 → LLM生成回答


# RAG核心知识


- RAG（检索增强生成）由三个核心模块组成：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           RAG 三大核心模块                                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐        │
│   │   ① 检索模块     │    │   ② 增强模块     │    │   ③ 生成模块     │        │
│   │   (Retrieve)    │───▶│   (Augment)     │───▶│   (Generate)    │        │
│   ├─────────────────┤    ├─────────────────┤    ├─────────────────┤        │
│   │ • 嵌入模型       │    │ • Prompt 拼接    │    │ • LLM 大模型     │        │
│   │ • 向量数据库     │    │ • 上下文窗口     │    │ • 流式输出       │        │
│   │ • 检索器         │    │ • 相关性过滤     │    │ • 答案生成       │        │
│   └─────────────────┘    └─────────────────┘    └─────────────────┘        │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```


| 模块         | 组件          | 作用                                                  |
| :----------- | :------------- | :----------------------------------------------------- |
| ① 检索模块 | 嵌入模型     | 将文本转换为向量（数学表示）                      |
|              | 向量数据库   | 存储和索引向量（Chroma、Pinecone、Weaviate） |
|              | 检索器        | 根据问题找到最相关的文档片段                      |
| ② 增强模块 | Prompt 拼接 | 将检索到的文档与原始问题组合                      |
|              | 上下文窗口   | 控制输入给 LLM 的内容长度                         |
|              | 相关性过滤   | 剔除不相关的检索结果                               |
| ③ 生成模块 | LLM 大模型   | 基于增强后的 Prompt 生成答案                     |
|              | 流式输出     | 实时返回生成结果                                    |
|              | 答案溯源     | 标注答案来源（引用文档）                           |



- 简要工作流程
```
PDF文档 → 分块(Chunking) → 向量化(Embedding) → 存入向量数据库
                    ↑
用户提问 → 向量化 → 相似度检索 → 召回相关块 → 拼接Prompt → LLM生成回答
```

- 五个核心步骤：加载 → 分块 → 嵌入 → 检索 → 生成



- RAG 核心公式

```py
# RAG 的数学表示
Answer = LLM(
    Prompt(
        Query,                    # 用户问题
        Retrieve(Query, KB)       # 从知识库检索的相关文档
    )
)

# 简化版
RAG(question) = LLM(question + search(question, knowledge_base))
```



# Chunking策略（分块）


原始文档通常很长（如一本书、一份财报），无法一次性全部输入 LLM。分块（Chunking）有两个核心目的：

| 目的 | 说明 |
| :--- | :--- |
| **适配上下文窗口** | LLM 有输入长度限制（如 4K、8K、128K tokens），分块后每次只送入相关片段 |
| **提升检索精度** | 小块更容易精确匹配用户问题，避免大段无关内容干扰 Embedding |

```text
不分块的问题：
┌─────────────────────────────────────────────┐
│ 整本书（100万 tokens）                       │
│ 问：主角叫什么？ → Embedding 被大量无关内容稀释 │
│ 结果：检索不到准确答案                        │
└─────────────────────────────────────────────┘

分块后：
┌──────────┐ ┌──────────┐ ┌──────────┐
│ 第1章    │ │ 第2章    │ │ ...      │
│ 主角出场  │ │ 情节发展  │ │          │
└──────────┘ └──────────┘ └──────────┘
问：主角叫什么？ → 精确匹配到第1章 → 准确回答
```

常见分块策略对比：

| 策略         | 说明                                                     | 优点             | 缺点            | 适用场景               |
| :----------- | :------------------------------------------------------- | :--------------- | :-------------- | :-------------------- |
| 固定大小分块 | 按固定字符数或 token 数切分                               | 简单、快速       | 会切断句子/段落 | 快速原型、简单文档     |
| 递归分块     | 按段落 → 句子 → 字符的优先级切分，尽量保持语义完整         | 保持自然边界     | 稍复杂          | 通用推荐               |
| 语义分块     | 利用 Embedding 计算句子间相似度，在语义变化处切分          | 语义完整性最好   | 计算开销大      | 高质量要求、长文档     |
| 重叠分块     | 块与块之间有重叠部分（如前一块的后10%与下一块的前10%重叠） | 避免边界信息丢失 | 增加存储和计算  | 重要文档、边界敏感任务 |

代码示例，用 LangChain 的 RecursiveCharacterTextSplitter
```py
from langchain.text_splitter import RecursiveCharacterTextSplitter

# 示例文档
document = """
第一章：AI 的起源

人工智能（AI）的概念最早可以追溯到 1950 年代。图灵测试是评估机器智能的经典方法。

第二章：机器学习

机器学习是 AI 的核心分支。深度学习通过多层神经网络实现了重大突破。

第三章：应用场景

AI 已广泛应用于图像识别、自然语言处理和推荐系统等领域。
"""

# 配置分块器
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=64,        # 每块最大字符数（实际使用建议 512-1024）
    chunk_overlap=20,      # 块之间重叠字符数（约 10-20%）
    separators=["\n\n", "\n", "。", "，", " ", ""],  # 按优先级切分
    length_function=len,   # 长度计算函数
)

# 执行分块
chunks = text_splitter.split_text(document)

# 查看结果
for i, chunk in enumerate(chunks):
    print(f"Chunk {i}: {chunk}\n")
```


输出为
```
Chunk 0: 第一章：AI 的起源

人工智能（AI）的概念最早可以追溯到 1950 年代。图灵测试是评估机器智能的经典方法。

Chunk 1: 第二章：机器学习

机器学习是 AI 的核心分支。深度学习通过多层神经网络实现了重大突破。

第三章：应用场景

Chunk 2: 第三章：应用场景

AI 已广泛应用于图像识别、自然语言处理和推荐系统等领域。

```

分块策略选择指南：
```text
我的文档是...
    │
    ├── 简单的纯文本、日志 → 固定大小分块
    │
    ├── 文章、报告、书籍 → 递归分块（推荐）
    │
    ├── 技术文档、学术论文 → 递归分块 + 重叠
    │
    └── 追求极致效果 → 语义分块
    
```


# Embedding原理


Embedding 是将文本转换为**固定长度的向量**（一串数字）的技术，让计算机能够理解和比较文本的语义。

```text
文本 → Embedding 模型 → 向量（如 768 维）

"苹果很好吃" → [0.12, -0.34, 0.56, ..., 0.78]  (768个数字)
"香蕉很香甜" → [0.11, -0.32, 0.55, ..., 0.79]  (语义相似的向量)
"今天天气不错" → [0.45, 0.23, -0.12, ..., 0.31]  (语义不同的向量)

相似度计算：苹果向量 · 香蕉向量 ≈ 0.95（高）
          苹果向量 · 天气向量 ≈ 0.32（低）
```


MTEB 的全称是 Massive Text Embedding Benchmark（大规模文本嵌入基准测试）。它是目前业界公认的、最全面、最权威的文本嵌入模型（Embedding Model）评估排行榜。
[Hugging face MTEB leaderboard](https://huggingface.co/spaces/mteb/leaderboard)这里有很多开源的嵌入模型。
一些示例模型如下：

| 模型系列               | 示例模型                                                     |
| :-------------------- | :---------------------------------------------------------- |
| BAAI/bge              | BAAI/bge-large-zh-v1.5                                      |
| Qwen3-Embedding       | Qwen/Qwen3-Embedding-0.6B                                   |
| sentence-transformers | sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2 |
| text2vec              | shibing624/text2vec-large-chinese                           |
| m3e                   | moka-ai/m3e-base                                            |

评估指标解释如下：
| 任务类型 | 中文含义 | 说明 | 应用场景 |
| :--- | :--- | :--- | :--- |
| Classification | 分类 | 判断文本属于哪个类别 | 垃圾邮件识别、情感分析、新闻分类 |
| Clustering | 聚类 | 将相似文本自动分组 | 客户分群、话题聚合、重复文档检测 |
| PairClassification | 配对分类 | 判断两段文本是否属于同一类别 | 重复问题检测、文本匹配 |
| Reranking | 重排序 | 对检索结果进行二次精排 | 搜索引擎优化、RAG 检索结果优化 |
| Retrieval | 检索 | 从海量文档中找到最相关的文档 | RAG 核心指标、信息检索、问答系统 |
| STS | 语义文本相似度 | 计算两段文本的语义相似程度 | 文本去重、相似度匹配、抄袭检测 |

代码示例：使用  [Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)
```py
from sentence_transformers import SentenceTransformer
import numpy as np

# 本地离线模型
model = SentenceTransformer("D:\\Devs\\local_models\\Qwen\\Qwen3-Embedding-0.6B", local_files_only=True)

# 模拟：文档被切分成不同长度的 chunks
chunks = [
    "北京",                                          # 2个字
    "中国的首都是北京。",                             # 10个字
    "北京是中华人民共和国的首都，位于华北平原北部。",    # 20个字
    "北京拥有悠久的历史，是中国的政治、文化中心..."     # 50个字
]

# 用户 Query（长短不一）
queries = [
    "首都",           # 2个字
    "中国的首都是哪里？",  # 10个字
    "请告诉我中国的首都是什么城市？"  # 15个字
]

# 编码所有 chunks（向量维度固定）
chunk_embeddings = model.encode(chunks)
print(f"Chunks 向量形状: {chunk_embeddings.shape}")  # (4, 1024)

# 编码 queries
for query in queries:
    query_embedding = model.encode([query])
    print(f"\nQuery: '{query}' -> 向量形状: {query_embedding.shape}")  # (1, 1024)
    
    # 计算相似度
    similarities = model.similarity(query_embedding, chunk_embeddings)[0]
    for chunk, sim in zip(chunks, similarities):
        print(f"  与 '{chunk[:20]}...' 相似度: {sim:.4f}")
```

# 向量数据库

向量数据库是专门用于存储和检索向量数据的数据库系统。

在 RAG 系统中，向量数据库扮演着“外部大脑”的角色：

```
原始文档 → Embedding 模型 → 向量 → 存入向量数据库
                                    ↓
用户问题 → Embedding 模型 → 查询向量 → 相似度检索 → 返回相关文档
```

核心能力：

- 向量存储：高效存储高维向量（如 768 维、1024 维）

- 相似度检索：通过余弦相似度、欧氏距离等算法，快速找到最相似的向量

- 向量索引：使用 HNSW、IVF 等算法加速检索，从“遍历所有向量”优化为“近似最近邻搜索”


主流向量数据库对比:

| 数据库    | 特点                      | 适用场景                 |
| :------- | :------------------------ | :---------------------- |
| Chroma   | 轻量级、嵌入式、零配置     | 本地开发、学习、原型验证 |
| Qdrant   | 高性能、云原生、过滤功能强 | 生产环境、中等规模       |
| Pinecone | 全托管、免运维、有免费额度 | 不想自己运维、快速上线   |
| Milvus   | 分布式、功能全面、开源     | 大规模生产（亿级向量）   |



Chroma 代码示例
```py
from langchain_community.embeddings import OllamaEmbeddings
from langchain_community.vectorstores import Chroma
from langchain_core.documents import Document

# ========== 1. 准备文档 ==========
documents = [
    Document(
        page_content="公司报销流程：填写报销单 → 主管审批 → 财务审核 → 出纳打款",
        metadata={"category": "财务"}
    ),
    Document(
        page_content="请假制度：需提前3天申请，紧急情况可电话请示",
        metadata={"category": "人事"}
    ),
    Document(
        page_content="考勤规则：工作时间 9:00-18:00，迟到需说明原因",
        metadata={"category": "人事"}
    ),
]

# ========== 2. 初始化 Embedding 模型 ==========
embeddings = OllamaEmbeddings(
    model="qwen3-embedding:0.6b",
    base_url="http://localhost:11434"
)

# ========== 3. 创建向量存储 ==========
vectorstore = Chroma.from_documents(
    documents=documents,
    embedding=embeddings,
    persist_directory="./langchain_chroma_db",   # 向量数据库保存目录
)

# ========== 4. 相似度检索 ==========
query = "怎么报销"
results = vectorstore.similarity_search(query, k=2)

print(f"🔍 查询：{query}")
for doc in results:
    print(f"   📄 {doc.page_content}")

# ========== 5. 带分数的检索 ==========
results_with_score = vectorstore.similarity_search_with_score(query, k=2)
for doc, score in results_with_score:
    print(f"   余弦距离: {score:.4f} | {doc.page_content[:30]}...")

# ========== 6. 转为检索器 ==========
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})
docs = retriever.invoke("请假")
```

输出结果：
```text
🔍 查询：怎么报销
   📄 公司报销流程：填写报销单 → 主管审批 → 财务审核 → 出纳打款
   📄 请假制度：需提前3天申请，紧急情况可电话请示
   余弦距离: 0.6790 | 公司报销流程：填写报销单 → 主管审批 → 财务审核 → 出...
   余弦距离: 1.0836 | 请假制度：需提前3天申请，紧急情况可电话请示...
```

`similarity_search_with_score` 原型，根据描述可知输出的是余弦距离，值越小，相似度越高。
```py
    def similarity_search_with_score(
        self,
        query: str,
        k: int = DEFAULT_K,
        filter: Optional[Dict[str, str]] = None,
        where_document: Optional[Dict[str, str]] = None,
        **kwargs: Any,
    ) -> List[Tuple[Document, float]]:
        """Run similarity search with Chroma with distance.

        Args:
            query (str): Query text to search for.
            k (int): Number of results to return. Defaults to 4.
            filter (Optional[Dict[str, str]]): Filter by metadata. Defaults to None.

        Returns:
            List[Tuple[Document, float]]: List of documents most similar to
            the query text and cosine distance in float for each.
            Lower score represents more similarity.
        """
```

值得注意的是，第一次运行会创建`langchain_chroma_db`目录，但如果重复运行，会重复的把相同的documents向量保存。所以实际运用时要注意去重处理。


- Chroma 核心操作速查表

| 操作 | 代码 | 说明 |
| :--- | :--- | :--- |
| 创建客户端 | `chromadb.PersistentClient(path="./db")` | 持久化存储 |
| 创建 Collection | `client.create_collection(name="my_docs")` | 创建表 |
| 插入文档 | `collection.add(documents=[...], ids=[...])` | 批量插入 |
| 检索 | `collection.query(query_embeddings=[...], n_results=3)` | 向量检索 |
| 过滤检索 | `collection.query(..., where={"field": "value"})` | 按元数据过滤 |
| 查看数量 | `collection.count()` | 文档总数 |
| 删除 Collection | `client.delete_collection("my_docs")` | 删除表 |
